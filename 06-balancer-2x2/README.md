# 6. Два на два с балансиром

Два входа в разных дата-центрах, два выхода в разных странах. На каждом мосте Xray раз в минуту проверяет,
какой выход отвечает быстрее, и ведёт трафик туда. Упал выход — через минуту все уже на втором.

```
            ┌──► мост 1 ──┐  балансир (leastPing)  ┌──► выход 1
телефон ────┤             ├────────────────────────┤
            └──► мост 2 ──┘                        └──► выход 2
```

## Файлы

| Файл | Куда |
|---|---|
| `bridge-outbounds.json` | 3X-UI → Настройки Xray → Исходящие: `to-exit-1`, `to-exit-2` |
| `bridge-observatory.json` | 3X-UI → Настройки Xray → вкладка Observatory |
| `bridge-routing.json` | 3X-UI → Маршрутизация: балансир `exits` + правила |
| `bridge-full.json` | мост целиком для голого Xray |
| `remnawave-bridge-profile.json` | Remnawave: профиль конфига для ноды-моста |

## 3X-UI

1. Выходы 1 и 2 — как в [схеме 2](../02-chain-3x-ui): у каждого свой домен (`exit1.`, `exit2.`) и свои ключи Reality.
2. На **каждом** мосте: оба исходящих, observatory и маршрутизация с балансиром.
   Правило для телефонов ведёт не в `outboundTag`, а в `balancerTag: exits`.
3. `fallbackTag: to-exit-1` — куда идти, пока observatory ещё ничего не измерил.
4. Телефону выдаёшь два подключения, по одному на мост. Клиент с автовыбором по пингу
   (urltest / «Авто») сам возьмёт живой вход.

## Remnawave

Мост — отдельная нода. В её профиле конфига (Config Profiles) входящее для пользователей,
а в исходящих — выходы. Клиентов в `inbounds[].settings.clients` не пишешь: их подставляет панель.
Выходы — обычные ноды или свои серверы. Для ссылки «через мост» в хосте указываешь адрес моста.

## Проверка

- Логи Xray на мосте: observatory пишет задержку до каждого выхода.
- Останови Xray на выходе 1 — через минуту трафик должен уйти на выход 2. Включи обратно.
